jianmu in Docker

Run jianmu on a server or a NAS that has no desktop: its gateway serves your models to agents on other computers, and you add providers and sign in to subscriptions from a page in your browser.

Imageghcr.io/DamonZS/Jianmu, for linux/amd64 and linux/arm64
Tagslatest (the newest release), daily (the newest release as of 20:00 UTC, moved once a day), stable (the desktop app's Stable channel: a release a week, out three days first, or an urgent one at once), 0.1.1150 (one release), 0.1, edge (every change on main)
Ports3425 the gateway agents call; 3430 the browser UI, when the container runs jianmu web; it answers the gateway’s /v1 routes too, so a reverse proxy needs only this port
Volume/config: providers, keys, sign-ins, plugins and usage
Usernonroot (uid 65532)

The image holds jianmu’s terminal-only build on Debian 12 slim, with bash for a terminal in the container and curl for the installers of the CLIs some subscriptions sign in with (Cursor, Devin, Grok Build). It runs jianmu serve (the gateway alone) unless given another command. The container finds no agents to wire, so jianmu in it is a gateway: the agents that use it run elsewhere.

Run it

Run it with the browser UI, a key for that page you keep across restarts, and both ports on the host’s loopback only:

Shell 
docker run -d --name jianmu --restart unless-stopped \
  -p 127.0.0.1:3425:3425 -p 127.0.0.1:3430:3430 \
  -e JIANMU_WEB_KEY=$(openssl rand -hex 16) \
  -v jianmu-config:/config \
  ghcr.io/DamonZS/Jianmu:latest web --addr 0.0.0.0:3430 --no-open

docker logs jianmu

The log names the page with its key:

Output 
● jianmu web on http://127.0.0.1:3430/?k=0f3c9a1e…
  on the network http://172.17.0.2:3430/?k=0f3c9a1e…
  these are the container's own addresses: other machines use the host's, and JIANMU_PUBLIC_URL=http://<host>:<port> puts it here
  other containers on this host http://172.17.0.1:3425
! anyone with the link can change jianmu and see its keys, and the network carries it unencrypted
  the link carries JIANMU_WEB_KEY · gateway http://127.0.0.1:3425 · Ctrl-C to stop
Agents outside the container need a gateway key. In the container any key works. A request from the host or another machine is answered only with an enabled gateway key, and gets 401 without one: make one as in Gateway keys. 127.0.0.1: in -p keeps a port on the host; leave it out, or name the host’s LAN or VPN address, for other machines to reach it.

Without web --addr 0.0.0.0:3430 --no-open the container runs the gateway alone, which you then set up from a terminal in it (docker exec -it jianmu jianmu provider add …). A folder bind-mounted at /config works in place of the named volume, if uid 65532 can write it: sudo chown -R 65532:65532 /volume1/docker/jianmu/config.

The browser UI

Open the link from the log. The key in it is traded for a cookie and taken out of the address; a page opened without it is turned away (401). With JIANMU_WEB_KEY set (16 or more letters, digits or - . _ ~; openssl rand -hex 16 makes one) the key stays the same across restarts and the browser stays signed in for 400 days. Without it, every start makes a new key and the cookie lasts the browser session.

The page is in gateway mode: Providers, Gateway, Routing, Usage, Sessions, Plugins and Settings, with no Agents, since there are no agents in the container. Library has its MCP servers alone, with the MCP router: other computers’ apps connect at the router’s address with a gateway key. Sessions lists only the sessions of agents on other computers that came through this gateway, never this machine’s agents’ files. Settings → General → Gateway mode turns it off.

On a NAS or a server you reach over SSH, open the page through a tunnel rather than publishing 3430: ssh -L 3430:127.0.0.1:3430 you@nas, then the log’s link on your own computer.

Anyone with the link can change jianmu and see its keys. Keep 3430 on loopback or a VPN. Across the network, serve it over HTTPS: give jianmu a certificate with JIANMU_TLS_CERT and JIANMU_TLS_KEY, or put it behind a reverse proxy with TLS, such as Caddy.

Sign in to subscriptions

Add API keys on Providers as on the desktop. A subscription’s sign-in (ChatGPT, Claude…) opens the vendor’s page in your browser, and when you are done the vendor sends that browser back to localhost, for ChatGPT http://localhost:1455/auth/callback?code=…. That is your own computer, not the container, so the page doesn’t load. Copy its whole address from the address bar and paste it into the sign-in’s Callback URL field.

The same from a terminal:

Shell 
docker exec -it jianmu jianmu accounts add codex

Open the link it prints, sign in, then paste the address the browser ended on. The browser UI can also import sign-ins from a file.

A Claude subscription is signed in to and answered through Claude Code, which the image doesn’t have. Have jianmu download Anthropic’s own build first: it says the version, where it comes from and where it goes, asks, and checks the download’s SHA-256 against Anthropic’s manifest. It is kept in /config/cache, on the volume, so a new image keeps it, and jianmu keeps it at Claude Code’s newest release by itself: it looks a minute after it starts and every six hours, and downloads a newer one the same way. Nothing needs installing again after an update. To hold a version, set -e DISABLE_AUTOUPDATER=1. jianmu accounts add claude offers it too when Claude Code is missing.

Shell 
docker exec -it jianmu jianmu claude-code install

A Grok (SuperGrok) subscription signs in through xAI’s Grok Build CLI, which the image doesn’t have either. Its sign-in, in the browser UI or with jianmu plugin login grok, installs it first, as xAI’s installer does: the stable version from x.ai/cli, kept in /config/home/.grok. To use a Grok Build binary you put on the volume yourself, set GROK_BIN_DIR to the folder holding it.

Your own browser

Jianmu Browser lets agents act in your own browser, through its extension. The extension can’t be loaded from the container’s folders, so in the browser UI open Library → Jianmu Browser and click Download the extension. The zip is pointed at the page’s own address, with a gateway key named Jianmu Browser of its own. Unzip it, open chrome://extensions, turn on Developer mode and click Load unpacked on the unzipped folder. An extension already loaded takes the address (http://localhost:3430, or the gateway’s published port) and a gateway key in its popup.

The Jianmu Browser key connects the extension and nothing else: it can’t use models, MCP servers or stats, so a copy of the zip left in Downloads spends nothing. The host’s browser reaches the container from Docker’s bridge, not from the container’s own computer, so it is that key’s alone and the container’s agents don’t use it yet (#5529). To use it from an agent on the host, give that agent a gateway key of its own with full access, connect the extension with the same key in its popup, and call /mcp/jianmu/browser with it. A browser given another key is that key’s alone, and it is let go once its key is turned off, removed or rotated.

What is kept

Everything jianmu writes is under /config, so a restart, or a new container on the same volume, keeps your providers, keys, sign-ins and plugins.

PathHolds
/config/jianmujianmu’s own files: settings.json, providers, gateway keys, routing groups
/config/homethe container’s HOME: sign-ins kept where their agent keeps them (~/.codex, ~/.claude…)
/config/cachethe model catalog, Bun, which plugins run on (downloaded the first time one is used), and the Claude Code jianmu claude-code install downloaded
/config/data, /config/statethe rest of what jianmu keeps

A volume made by an older image keeps working: jianmu adds the folders it lacks when it starts. Only sign-ins made with that older image, which lived outside the volume, have to be made again.

Environment

VariableWhat it does
JIANMU_ADDRwhere the gateway listens. The image sets 0.0.0.0:3425, so the published port reaches it.
JIANMU_PUBLIC_URLthe address other machines reach the gateway at, such as http://192.168.1.20:3425 (the host’s or the NAS’s, on the published port), or a reverse proxy’s base URL. In the container jianmu sees only Docker’s own 172.17.x address; with this set, the address it shows and prints is the one to use.
JIANMU_WEB_KEYthe browser UI’s key, kept across restarts (16+ characters)
JIANMU_TLS_CERT, JIANMU_TLS_KEYa PEM certificate (its chain after it) and its key, mounted into the container: other machines then reach the gateway and the browser UI over https:// only, and plain HTTP from them gets 400. The files are read again when they change, so a renewal needs no restart. One without the other, or files that don’t load, stop jianmu from starting. Use https:// in JIANMU_PUBLIC_URL too.
JIANMU_ALLOW_IPSthe only addresses other machines may reach the gateway and the browser UI from, as IPs and CIDR ranges: 203.0.113.7,10.0.0.0/8,2001:db8::/32. Any other address gets 403, even with a gateway key. Unset lets every address in, each with a key. See Allowed addresses.

Gateway keys and other machines

  1. Make a key for each clientGateway → Gateway keys, or in a terminal docker exec jianmu jianmu gateway-key add "Laptop", which prints the new sk-jianmu-key-…. Every request from outside the container, the host’s own included, must carry an enabled gateway key, and one without gets 401. A key can have its own daily, weekly, monthly, every-N-days or every-N-hours limit and its own list of models (jianmu gateway-key limit, jianmu gateway-key models).
  2. Publish the portRecreate the container with -p 3425:3425, or bound to the NAS’s LAN or VPN address (-p 192.168.1.20:3425:3425), and with -e JIANMU_PUBLIC_URL=http://192.168.1.20:3425.

On each other computer, point the agent at the gateway with one of those keys as its API key: http://192.168.1.20:3425/v1 for an OpenAI client, http://192.168.1.20:3425 for an Anthropic or Gemini one. Model ids are provider/model, or a routing group’s; GET /v1/models lists them. If that computer runs jianmu itself, add the container as a Remote jianmu instead, and jianmu wires its agents for you.

Other containers on the same host. Another container on the NAS reaches jianmu at the host, through the Docker bridge’s gateway and the published port: http://172.17.0.1:3425 on Docker’s default bridge. The container’s own 172.17.x address is no use to it, and the host’s LAN address may not be either, as a NAS’s firewall can keep containers from it. host.docker.internal is the same address on Docker Desktop, and on Linux only in a container given extra_hosts: ["host.docker.internal:host-gateway"]. A container on jianmu’s own compose network, or one you made, can use its name, http://jianmu:3425. Either way it sends a gateway key. The log and the browser UI list this address as Other containers on this host, after the host’s address the page was opened at.

Settings → Network and sharing → Share on local network isn’t needed in the container: turning it on also makes a gateway key named Jianmu, and the gateway asks for a key from outside the container either way.

Upgrading from an earlier image. An agent outside the container that sends jianmu, or any other key that isn’t an enabled gateway key, now gets 401 (“the API key sent is not an enabled jianmu gateway key”). Make it a key as above and put that in the agent’s settings. Agents that already send a gateway key, and a Remote jianmu set up with one, keep working.

Allowed addresses. On a public host, set -e JIANMU_ALLOW_IPS=203.0.113.7,10.0.0.0/8 to the addresses your clients come from. A request from any other address is refused 403 before its key is looked at, so a key that leaks is no use from elsewhere; the refusal names the address it came from, as does the container’s log. jianmu judges the address of the connection itself, never an X-Forwarded-For header, and a mistyped entry lets nothing in rather than everything. Docker’s default bridge network passes a client’s own address into the container, but a request from the host itself arrives from the bridge’s gateway (172.17.0.1), and Docker Desktop and rootless Docker show every client as one address of their own: add that, or check what the 403 says. Behind a reverse proxy or tunnel, every request comes from the proxy’s address, so limit who reaches jianmu at the proxy. On the desktop app the same list is Settings → Network and sharing → Allowed addresses.

Over the internet, prefer a VPN such as Tailscale or WireGuard to opening 3425. A reverse proxy or tunnel in front of the container is the network too: its clients need a gateway key like any other machine’s.

Claude Code’s status line, with Claude Code outside the container. The status line square can’t reach another machine’s ~/.claude/settings.json, and the command it writes names a binary in the container. The gateway answers the same line itself: on the machine Claude Code runs on, set statusLine in ~/.claude/settings.json to {"type": "command", "command": "curl -fsS -m 1 -H 'Authorization: Bearer sk-jianmu-key-…' --data-binary @- http://<host>:3425/v1/jianmu/statusline || true"}, with the host or address that reaches the container and a gateway key (a read-only key is enough). A key held to a budget, models or accounts gets the line once its owner turns on Quotas for it, with only the accounts it may use. Add ?format=json for the same as JSON (the line, the model, and each account’s windows with used and resetsAt), for a status line that draws its own. Claude Code runs it on every message and passes its session on stdin, which adds the model the session went to. The same command is shown in the browser UI under Settings → About.

Docker Compose on a NAS

compose.yaml 
services:
  jianmu:
    image: ghcr.io/DamonZS/Jianmu:latest
    restart: unless-stopped
    ports:
      # 127.0.0.1: the host alone; every caller outside the container needs a gateway key
      - "127.0.0.1:3425:3425"
      - "127.0.0.1:3430:3430"
    environment:
      JIANMU_PUBLIC_URL: http://<nas-address>:3425
      JIANMU_WEB_KEY: <random-key>
    volumes:
      - ./config:/config
    command: [web, --addr, 0.0.0.0:3430, --no-open]

Then: sudo chown -R 65532:65532 ./config, docker compose up -d, open http://127.0.0.1:3430/?k=<random-key> through an SSH tunnel, add your providers and make a gateway key for each machine. For other machines to reach the gateway, change its line to "3425:3425" (or the NAS’s LAN or VPN address) and run docker compose up -d again.

Health, terminal, updates

  • Health. The image has a HEALTHCHECK: jianmu healthcheck exits 0 while the gateway answers, under serve and web alike, so docker ps shows the container as healthy and Compose can wait for it with depends_on: condition: service_healthy.
  • Terminal. docker exec -it jianmu bash, or a NAS panel’s terminal, opens a shell with jianmu on its PATH: jianmu providers, jianmu models, jianmu usage, jianmu quota and the rest of the CLI.
  • Updates. Pull the new image and recreate the container on the same volume: docker pull ghcr.io/DamonZS/Jianmu:latest, then docker rm -f jianmu and the same docker run, or docker compose pull && docker compose up -d. jianmu releases several times a day; for one update a day with Renovate or Watchtower, follow daily (with Renovate, pin its digest), or stable for one a week.
  • Build it yourself. docker build -t jianmu . in a checkout of the repository makes the same image.
